# GadgetMoTo Product Color Variant Schema

## Checkpoint boundary

Migration 11 is defined locally in
`20260802103548_product_color_variant_schema.sql`. It has not been dry-run,
deployed, or executed. The ten earlier migrations are deployed, synchronized,
and unchanged.

This checkpoint creates only the forward migration and its documentation. It
does not add color records, admin color controls, storefront swatches, cart or
checkout UI, AJAX pagination, image uploads, environment values, or browser
database access. Those application changes must wait until Migration 11 has
been manually reviewed, dry-run, deployed, and confirmed in both local and
remote migration history.

## Why colors are product-level

`product_variants` currently represents the confirmed purchasable RAM/storage
configuration with a canonical SKU and price. A color does not have a
business-supplied SKU, price, or inventory record, so treating each color as a
commercial product variant would invent commerce data and duplicate the
existing catalog model.

Migration 11 therefore adds `public.product_color_variants`, owned directly by
`public.products`. No relationship to `product_variants` is introduced. A
future migration may add color-specific commerce relationships only after the
business supplies authoritative SKU, pricing, or inventory data.

## Table definition

`public.product_color_variants` contains:

- `id` — UUID primary key generated by PostgreSQL
- `product_id` — required product foreign key
- `name` — required trimmed display name with administrator capitalization
  preserved
- `normalized_name` — generated lowercase, trimmed value used only for
  duplicate detection
- `hex_code` — optional `#RRGGBB` display value
- `is_active` — publication control, defaulting to active
- `sort_order` — nonnegative display order
- `created_at` and `updated_at` — database timestamps

Deleting an otherwise deletable draft product cascades to its color records.
This does not bypass the existing guarded product-deletion rules. Deleting a
color referenced by an order clears only the live color reference; the order's
immutable name snapshot remains.

## Integrity rules

- Names cannot be blank and must already be trimmed before storage.
- `normalized_name` is generated by the database as
  `lower(btrim(name))`.
- `(product_id, normalized_name)` is unique. `Black`, `black`, `BLACK`, and
  ` Black ` therefore cannot become separate colors for one product.
- `sort_order` cannot be negative.
- `hex_code` is nullable. When supplied it must contain exactly `#` followed
  by six hexadecimal digits. Names without an authoritative hex value use a
  neutral text-labeled swatch later.
- No color SKU, price, inventory quantity, or seed color is created.

## Storefront read boundary

The base table has RLS enabled. The dedicated non-login
`gadgetmoto_storefront_reader` role can read only active colors whose products
are publicly visible as either live catalog products or approved Coming Soon
previews. The security-invoker `storefront.product_colors` view exposes only:

- color ID
- product ID
- display name
- optional hex code
- sort order

The view and base-table policy are server-only. `public`, `anon`, and ordinary
`authenticated` users receive no direct storefront read or write path. No Data
API or browser credential is introduced.

## Administrator policies and audit

The `authenticated` role receives table privileges, but RLS allows select,
insert, update, and delete only when the existing
`public.is_active_administrator()` helper confirms the authenticated user has
an active `staff_profiles` row with role `administrator`.

A trigger writes one minimized `audit_logs` entry for each administrator color
insert, update, or delete. Audit JSON contains only the owning product ID and
changed field names. It does not copy color values, credentials, request
bodies, or other private data.

## Cart and order decision

The current browser cart identifies a line by product slug and RAM/storage
variant. Migration 11 does not change the cart contract because application
work is intentionally blocked until deployment.

The current `order_items` table has immutable product, brand, variant, SKU, and
price snapshots but no selected-option metadata. Migration 11 therefore adds
the smallest compatible storage:

- nullable `color_variant_id`
- nullable `color_name_snapshot`

Existing orders remain valid because both fields are nullable. Products with
no active colors continue to require no color. A database trigger validates
that a supplied color is active and belongs to the order item's product, then
derives the name snapshot from the trusted database row rather than browser
text. When a product has active colors, new order items require a valid color.
Renaming or deleting a color later does not rewrite the historical snapshot.

After deployment, the application phase must extend cart line identity,
checkout contract validation, server catalog reads, and order insertion to use
the database color ID. It must never trust a browser-supplied color name.

## Indexes and update behavior

- The unique `(product_id, normalized_name)` constraint supports duplicate
  detection.
- A partial `(product_id, sort_order, id)` index supports stable active-color
  ordering.
- A partial `order_items(color_variant_id)` index supports historical reference
  lookup.
- The existing controlled `public.set_updated_at()` trigger maintains color
  `updated_at` values.

## Deployment gate

Only after manual review may the project owner run:

```powershell
npx.cmd supabase migration list --linked
npx.cmd supabase db push --linked --dry-run
npx.cmd supabase db push --linked
npx.cmd supabase migration list --linked
```

Migration 11 must appear under both Local and Remote before color management,
storefront color selection, cart/checkout integration, or AJAX admin
pagination begins. A Git push alone does not satisfy this gate.
