# GadgetMoTo Commerce Migration 3 Plan

## Status and scope

This document records the reviewed plan and local draft for Commerce Migration 3. The migration remains unexecuted. It covers seven commerce tables plus one foreign-key addition to the existing inventory movement table. It does not implement order submission, inventory reservation, payment integration, staff policies, or customer accounts.

Exact public order-number generation and VAT handling remain unresolved. Guest orders will eventually be created only through trusted server-side workflows, never unrestricted browser writes.

## `staff_profiles`

Purpose: application-specific staff authorization linked to Supabase Auth. Customer profiles are not part of launch scope.

Planned columns:

| Column | Definition |
| --- | --- |
| `user_id` | `uuid primary key` |
| `display_name` | `text not null` |
| `role` | `public.staff_role not null` |
| `is_active` | `boolean not null default true` |
| `created_at` | `timestamptz not null default now()` |
| `updated_at` | `timestamptz not null default now()` |

- Foreign key: `user_id -> auth.users(id)` with `ON UPDATE CASCADE` and `ON DELETE CASCADE`.
- Constraint: trimmed `display_name` must not be blank.
- Index: `(role, is_active)` only where staff-management queries justify it.
- Security: no public reads or writes; authorization comes from controlled database records, never client-controlled user metadata. Enable RLS immediately, revoke `anon` and `authenticated`, and defer staff policies to a dedicated access migration.

## `orders`

Purpose: submitted guest orders and commercial status. Customer accounts are not required.

Planned columns:

| Column | Definition |
| --- | --- |
| `id` | `uuid primary key default gen_random_uuid()` |
| `public_order_number` | `text not null` |
| `status` | `public.order_status not null default 'pending_review'` |
| `customer_full_name` | `text not null` |
| `customer_mobile` | `text not null` |
| `customer_email` | `text not null` |
| `delivery_method` | `public.delivery_method not null` |
| `payment_method` | `public.payment_method not null` |
| `merchandise_subtotal_centavos` | `bigint not null` |
| `vat_rate_bps` | `integer null` |
| `vat_amount_centavos` | `bigint null` |
| `delivery_fee_centavos` | `bigint null` |
| `final_total_centavos` | `bigint null` |
| `customer_notes` | `text null` |
| `internal_notes` | `text null` |
| `consent_privacy_at` | `timestamptz not null` |
| `consent_terms_at` | `timestamptz not null` |
| `consent_final_review_at` | `timestamptz not null` |
| `reviewed_by` | `uuid null` |
| `reviewed_at` | `timestamptz null` |
| `confirmed_at` | `timestamptz null` |
| `cancelled_at` | `timestamptz null` |
| `created_at` | `timestamptz not null default now()` |
| `updated_at` | `timestamptz not null default now()` |

- Foreign key: `reviewed_by -> public.staff_profiles(user_id)` with `ON UPDATE CASCADE` and `ON DELETE SET NULL`.
- Constraints: public number and customer name/mobile/email are nonblank; public number is unique; monetary values are nonnegative when supplied; VAT basis points are between 0 and 10000 when supplied; `cash_on_pickup` is allowed only with `store_pickup`; reviewer and review timestamp are either both null or both populated. Final total may remain null until VAT and delivery are confirmed.
- Indexes: unique public number; `(status, created_at desc)`; `(customer_email, created_at desc)` only if the operational lookup justifies indexing personal data.

No VAT rate is assumed. Candidate public-order-number strategies are:

1. A cryptographically random customer-facing identifier generated by the trusted server.
2. A controlled database function combining a safe prefix, date component, and random value.
3. An internal sequence used only internally and never directly exposed to customers.

A non-sequential public identifier is recommended, but its exact format remains unresolved.

## `order_addresses`

Purpose: preserve the delivery-address snapshot used for an order.

| Column | Definition |
| --- | --- |
| `id` | `uuid primary key default gen_random_uuid()` |
| `order_id` | `uuid not null` |
| `street_address` | `text not null` |
| `province` | `text not null` |
| `city_municipality` | `text not null` |
| `barangay` | `text not null` |
| `postal_code` | `text not null` |
| `created_at` | `timestamptz not null default now()` |

- Foreign key: `order_id -> public.orders(id)` with `ON UPDATE CASCADE` and `ON DELETE CASCADE`.
- Constraints: unique `order_id`; every address field is nonblank.
- Delivery orders require one snapshot; store-pickup orders require none. The trusted order transaction enforces this cross-table rule. There is no reusable customer address book at launch.

## `order_items`

Purpose: immutable purchase-time product, variant, and price snapshots.

| Column | Definition |
| --- | --- |
| `id` | `uuid primary key default gen_random_uuid()` |
| `order_id` | `uuid not null` |
| `product_id` | `uuid null` |
| `variant_id` | `uuid null` |
| `product_name_snapshot` | `text not null` |
| `brand_name_snapshot` | `text not null` |
| `variant_snapshot` | `text not null` |
| `sku_snapshot` | `text not null` |
| `unit_price_centavos` | `bigint not null` |
| `quantity` | `integer not null` |
| `line_total_centavos` | `bigint not null` |
| `created_at` | `timestamptz not null default now()` |

- Foreign keys: order uses `ON UPDATE CASCADE`, `ON DELETE CASCADE`; product and variant use `ON UPDATE CASCADE`, `ON DELETE SET NULL`.
- Constraints: all snapshot text is nonblank; unit and line prices are nonnegative; quantity is 1 through 99; line total equals unit price multiplied by quantity.
- Index: `order_id`.
- Product and variant references become informational after purchase. Snapshot fields remain authoritative for historical display. Browser prices are never authoritative; trusted server logic loads canonical prices and creates snapshots transactionally.

## `payments`

Purpose: payment attempts, instructions, and staff-confirmed status. Multiple attempts may belong to one order.

| Column | Definition |
| --- | --- |
| `id` | `uuid primary key default gen_random_uuid()` |
| `order_id` | `uuid not null` |
| `method` | `public.payment_method not null` |
| `status` | `public.payment_status not null default 'pending'` |
| `amount_centavos` | `bigint null` |
| `external_reference` | `text null` |
| `provider_checkout_id` | `text null` |
| `provider_payment_id` | `text null` |
| `proof_storage_path` | `text null` |
| `staff_notes` | `text null` |
| `verified_by` | `uuid null` |
| `verified_at` | `timestamptz null` |
| `created_at` | `timestamptz not null default now()` |
| `updated_at` | `timestamptz not null default now()` |

- Foreign keys: order uses `ON UPDATE CASCADE`, `ON DELETE CASCADE`; verifier uses `ON UPDATE CASCADE`, `ON DELETE SET NULL`.
- Constraints: amount is nonnegative when supplied; optional identifiers/notes are not all whitespace; verifier and timestamp are both null or both populated.
- Indexes: `(order_id, created_at)` and partial unique indexes for each supplied external reference, provider checkout ID, and provider payment ID.
- Browser redirects never establish payment success. Maya later requires verified server-side provider data or webhook processing. Manual proof storage is deferred.
- Never store card numbers, CVVs, passwords, GCash PINs, Maya secret keys, or complete banking credentials.

## `payment_events`

Purpose: append-only provider and staff payment workflow events.

| Column | Definition |
| --- | --- |
| `id` | `uuid primary key default gen_random_uuid()` |
| `payment_id` | `uuid not null` |
| `event_type` | `text not null` |
| `external_event_id` | `text null` |
| `payload` | `jsonb null` |
| `created_at` | `timestamptz not null default now()` |

- Foreign key: `payment_id -> public.payments(id)` with `ON UPDATE CASCADE` and `ON DELETE CASCADE`.
- Constraints: event type is nonblank; supplied payload is a JSON object; supplied external event ID is unique.
- Indexes: `(payment_id, created_at)` and a partial unique external-event index.
- No `updated_at` column or trigger. Provider IDs support idempotency. Payloads are minimized and stripped of secrets; full payment credentials are never logged.

## Inventory movement staff reference

Commerce Migration 3 will add a foreign key from the existing nullable `public.inventory_movements.created_by` column to `public.staff_profiles(user_id)`, using `ON UPDATE CASCADE` and `ON DELETE SET NULL`. It belongs here because `staff_profiles` will then exist. Deployed Inventory Migration 2 remains immutable.

## `updated_at` strategy

The existing `public.set_updated_at()` helper is planned for `staff_profiles`, `orders`, `order_fulfillments`, and `payments`. It is not planned for `order_addresses`, `order_items`, or `payment_events`. Address/item snapshots represent purchase-time facts, and events are append-only; these records must not be casually rewritten.

## Trusted order-creation transaction

Commerce Migration 3 creates protected tables only. A later trusted server workflow will:

1. Receive validated guest checkout data through a trusted endpoint.
2. Normalize customer contact details.
3. Load canonical products and variants from PostgreSQL.
4. Reject inactive or unavailable variants.
5. Lock required inventory rows to prevent overselling.
6. Recalculate unit prices and merchandise subtotal server-side.
7. Validate delivery/payment compatibility.
8. Create the order.
9. Create an address snapshot for delivery.
10. Create immutable order-item snapshots.
11. Create the initial fulfillment.
12. Create an initial payment when appropriate.
13. Reserve inventory and write movements through a later reviewed transactional function.
14. Commit all successful changes atomically.
15. Roll back every change if any required step fails.

No unrestricted anonymous insert policy is planned.

## Order-total integrity

- Merchandise subtotal comes from order-item snapshots whose canonical prices were loaded server-side.
- VAT remains nullable until business tax treatment is confirmed; no VAT rate is invented.
- Delivery fee remains nullable until delivery is reviewed.
- Final total remains nullable until all required components are known.
- Browser-provided subtotals and final totals are never trusted.
- Trusted server totals are calculated inside the order transaction.
- Exact final-total constraint logic is deferred until VAT treatment is confirmed.

## Security, RLS, and privileges

All seven new tables will enable RLS immediately, create no policies, revoke all table privileges from `anon` and `authenticated`, add no public grants, keep Data API access unavailable, and introduce no public read/write path.

| Access group | Planned access |
| --- | --- |
| `anon` | No direct access |
| Authenticated non-staff | No direct access |
| Active staff | Policies deferred to the dedicated staff-access migration |
| Service/server | Trusted server operations only |

Service-role credentials must never enter browser code. Future guest submission may use a trusted server route, Edge Function, or narrowly reviewed security-definer function—not a permissive anonymous table policy.

## Privacy boundaries

- Orders contain personal information and are never publicly readable.
- Customer data is not stored in browser `localStorage`.
- Payment secrets and card credentials are prohibited.
- Internal notes never appear in public storefront responses.
- Logging minimizes customer and payment information.
- Retention/deletion rules require business and legal review; no retention period is assumed.

## Index plan

- `staff_profiles(role, is_active)` where operationally useful.
- Unique `orders.public_order_number`; `orders(status, created_at desc)`; optional `(customer_email, created_at desc)` when justified.
- Unique `order_addresses.order_id`.
- `order_items.order_id`.
- Unique `order_fulfillments.order_id`.
- `payments(order_id, created_at)` plus partial unique external reference, checkout ID, and payment ID indexes.
- `payment_events(payment_id, created_at)` plus partial unique external event ID.

No speculative index is planned without an expected query.
